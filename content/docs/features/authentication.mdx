App: `features/auth` · Backend: Supabase Auth (`auth.users`).

Lynx uses **email + password** authentication. Email verification (after
sign-up) and password reset both use a **numeric OTP code** — there are **no
magic-link deep links** in v1. Google/Apple SSO exists but is gated off
(`--dart-define=ENABLE_SSO=true`) until accounts warrant it.

<Callout type="info">
A **login account is not a client record**. Signing up creates an `auth.users`
row; it only becomes useful once it's linked to a `person` (via an
[invite code](/docs/features/clients-and-invites) at finish-setup, or by staff
seeding). See [the core model](/docs/index#core-model-in-one-paragraph).
</Callout>

## Screens & flow

| Screen | Route | What it does |
| --- | --- | --- |
| Splash | `/splash` | Fades the logo; routes to `/welcome` (no session) or `/app`. |
| Welcome | `/welcome` | Brand mark + **Create an account** / **Log in**. |
| Login | `/login` | Email + password → `signInWithPassword`. Has **Forgot password?**. |
| Sign up | `/signup` | Email + password (+ repeat) with live password requirements → `signUp`. |
| Verify email | `/verify-email?email=` | 6-digit code → `verifyOTP(type: signup)`. Resend supported. |
| Forgot password | `/forgot-password` | Email → `resetPasswordForEmail` (sends a code). |
| Reset password | `/reset-password?email=` | Code + new password → `verifyOTP(type: recovery)` then `updateUser`. |

### Sign-up
1. `AuthRepository.signUp(email, password)` → Supabase sends a **Confirm signup**
   email whose `{{ .Token }}` is the 6-digit code.
2. User enters the code → `verifySignupOtp` (`OtpType.signup`) establishes the
   session → `/splash` → `/app`.
3. A brand-new account isn't linked to a person yet, so `RootShell` shows
   **finish-setup** (redeem an invite) until it is.

### Password reset
1. `sendPasswordResetOtp(email)` → **Reset password** email with `{{ .Token }}`.
2. On `/reset-password`, `verifyRecoveryOtp` (`OtpType.recovery`) opens a
   temporary recovery session — the router's `isRecovering` latch **pins the user
   here** so the recovery session isn't treated as a normal login.
3. `updatePassword` sets the new password; the app **signs out** and returns to
   `/login` so the user re-authenticates with the new password.

## Password requirements

Enforced client-side (`PasswordRequirements` + `validation_helpers`), shown live:
at least **8 characters**, one **uppercase**, one **lowercase**, one **special
character**.

## Repository

`AuthRepository` (static methods, repository pattern) wraps Supabase Auth and
throws friendly `AppException`s: `signInWithPassword`, `signUp`,
`verifySignupOtp`, `resendSignupOtp`, `sendPasswordResetOtp`,
`verifyRecoveryOtp`, `updatePassword`, `signInWithOAuth` (gated), `signOut`.

## Supabase configuration

<Callout type="warn">
OTP delivery **requires the email templates to surface `{{ .Token }}`** (not just
`{{ .ConfirmationURL }}`). Edit **Confirm signup**, **Magic Link**, and **Reset
password** templates. The default OTP length is 6; change it under Auth settings
if you want 8. Production email goes through **custom SMTP** (Brevo) with a
verified sender domain — the built-in sender is rate-limited and testing-only.
</Callout>

## Branding

The **welcome** screen shows a full-bleed hero image
(`assets/images/welcome_hero.jpg`) with the brand mark stacked on top; a scrim
darkens the top for legibility and melts the image into the cream actions area.
If the image is missing it falls back to a forest gradient. The splash screen
renders `assets/icons/logo.png` (a placeholder forest-on-cream **L** monogram);
the launcher icon is generated by `flutter_launcher_icons` from
`assets/icons/app_icon.png`. The hero image, logo, name (`appName`) and tagline
(`welcomeTagline`) are all **brand variables**.

<Callout type="info">
**White-labeling (later, not now).** The brand-facing values are already
centralised — name/tagline live in the l10n arb (`appName`, `welcomeTagline`),
colours in `AppColors`, and the hero/logo/icon are single named assets. That's
enough groundwork that per-gym rebranding is a config/asset swap, not a refactor.
Building the full runtime theming pipeline (per-tenant brand fetched from the
backend, or per-client build flavors) waits until there's a second paying
gym — the customization surface and app-store strategy aren't known pre-launch,
so building it now would be speculative.
</Callout>
